# libcamera 설계 문서

**카메라 API부터 Pipeline Handler와 IPA까지, 코드 구조와 근거를 함께 읽는 문서입니다.**

이 문서는 공개 libcamera 소스를 분석해 만든 검토용 설계 문서입니다. libcamera 공식 문서의 탐색 구조와 OMM의 읽기 중심 디자인을 적용했습니다.

## 읽는 순서

1. **시스템 개요**에서 소스가 어떤 패키지로 나뉘는지, 패키지 사이의 의존이 어느 방향인지 먼저 확인하세요.
2. **핵심 시나리오 시퀀스**에서 요청이 제출되고 완료될 때까지 호출이 지나가는 순서를 따라가세요.
3. **카메라와 요청 모델**에서 공개 API의 선언을, **Pipeline Handler**에서 공통 클래스와 하드웨어별 구현의 관계를, **IPA 관리와 구현 진입점**에서 알고리즘 모듈의 관리 구조를 확인하세요.
4. **IPU3 LSC** 두 문서는 한 알고리즘을 끝까지 따라가는 예입니다.

각 페이지 끝의 "다음 단계" 링크가 이 순서를 그대로 잇습니다.

각 페이지에는 추출한 클래스, 구조 설명, 관계 그림과 코드 근거가 있습니다. 관계 그림을 누르면 확대하거나 클래스 이름을 검색할 수 있습니다. 소스 링크는 분석에 사용한 커밋의 파일과 줄로 연결됩니다.

왼쪽 메뉴에서 목차에 딸린 하위 문서는 접었다 펼 수 있습니다. 읽고 있는 가지만 펴 둡니다.

시나리오 문서의 번호 목록에는 로깅과 단순 접근자 호출을 싣지 않고, 뺀 개수를 각 페이지에 적었습니다. 메서드를 큐나 신호에 넘기는 자리는 **예약된 호출**로 표시했습니다. 그 지점부터는 실행 시점과 스레드를 정적 분석으로 확인할 수 없으므로, 번호 목록이 이후의 순서를 보증하지 않습니다.

## 검토 상태 읽기

모든 생성 문서는 **사람 검토 전**입니다. `ok`는 자동 인용 검사를 통과했다는 뜻이며, 설명의 정확성이 승인되었다는 뜻은 아닙니다. `needs-review`는 인용 검사에서도 확인할 문제가 남아 있다는 뜻입니다.

이번 갱신에서는 12개 페이지 모두 자동 검사를 통과했습니다. 문장의 정확성은 아직 사람이 확인하지 않았습니다. 자동 검사는 인용 위치가 실제로 존재하는지, 문장이 가리키는 이름이 추출한 사실에 있는지, 문장 형태가 규칙을 지키는지만 봅니다. 클래스 관계 그림은 정적으로 추출한 상속·필드 관계를 보여 주며 실행 순서나 실기기 동작을 보증하지 않습니다.

## 분석과 배포 범위

분석 기준은 libcamera 커밋 `279d355ef8f7a4f98bb0a3004c0f788387814506`입니다. WSL2에서 IPU3·RKISP1·UVC와 GStreamer를 포함해 빌드했고, 문장은 Windows의 로컬 Ollama로 생성했습니다. 호출 순서는 libclang으로 추적했으며 진입 함수 5개를 모두 찾았습니다. 실기기 촬영과 실행 검증은 후속 작업입니다.

[camera-hal-sdd](https://github.com/TTolsun/camera-hal-sdd)는 분석·생성·검증·화면 구성 기술을 관리합니다. [libcamera-sdd](https://github.com/TTolsun/libcamera-sdd)는 원본 소스 이력과 완성 문서의 배포를 담당합니다. 자동 갱신 작업은 아직 연결하지 않았습니다.

원래 라이브러리의 사용법은 [libcamera 공식 문서](https://docs.libcamera.org/master/)에서 확인할 수 있습니다.
