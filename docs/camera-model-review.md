# 공개 카메라 모델 문서의 충분성 검토

**판정: 소스 탐색용 초안으로는 사용할 수 있지만, Camera HAL 설계 검토에 사용할 문서로는 부족합니다.** 2026-09-21에 [게시된 카메라와 요청 모델](https://ttolsun.github.io/libcamera-sdd/camera-model.html)의 실제 HTML을 확인했습니다. 표시된 분석 기준은 `279d355ef8f7a4f98bb0a3004c0f788387814506`이며 사람 검토 전, 인용 검사 `needs-review` 상태입니다.

## 현재 확인할 수 있는 내용

클래스 세 개의 선언 위치와 기반 클래스, 원본 커밋, 다음 문서 링크를 확인할 수 있습니다. 그림은 다섯 노드와 다섯 상속 관계를 표시합니다. 구조 탐색의 시작점과 원문 접근 경로는 마련되어 있습니다.

## 보완이 필요한 내용

| 우선순위 | 관찰한 문제 | 설계 검토에 미치는 영향 | 완료 기준 |
|---|---|---|---|
| 높음 | 세 클래스의 책임이 모두 “확인 필요”입니다. | 변경을 어느 클래스에서 처리할지 판단하기 어렵습니다. | CameraManager·Camera·Request의 책임과 연결 관계를 각각 코드 근거로 설명합니다. |
| 높음 | 설명이 한 문단이며 본문의 대괄호 인용은 검사 규약을 충족하지 않습니다. | 설명을 검증 가능한 근거와 연결하지 못했습니다. | 유효한 인용 형식과 링크를 만들고 문장이 근거의 의미와 일치하는지 검토합니다. |
| 높음 | Request의 생성·버퍼 연결·완료·재사용 설명이 없습니다. | 요청 처리와 버퍼 수명을 이해할 수 없습니다. | 정상 요청 한 건의 순서, 소유권·수명, 완료 통지·재사용 조건을 설명합니다. |
| 높음 | 카메라 상태 전이, 실패·취소·종료 계약이 없습니다. | 잘못된 상태의 호출과 종료 중 자원 해제 문제를 검토할 수 없습니다. | 상태별 허용 호출과 오류, 중단 시 남은 요청·버퍼 처리를 명시합니다. |
| 높음 | 스레드와 동기화 제약을 설명하지 않습니다. | 정적 관계 그림만으로 호출 안전성을 오해할 수 있습니다. | 코드에서 확인한 제약과 실행으로 확인해야 할 항목을 구분합니다. |
| 보통 | 그림이 Object·Extensible 상속만 보여 줍니다. | CameraManager·Camera·Request의 사용 흐름을 설명하지 못합니다. | 상속 그림과 별도로 근거가 확보된 상태도·요청 흐름을 제공합니다. |

동일 커밋의 소스에는 보완에 사용할 근거가 있습니다. [Camera의 상태와 동기화 설명](https://github.com/TTolsun/libcamera-sdd/blob/279d355ef8f7a4f98bb0a3004c0f788387814506/src/libcamera/camera.cpp#L771), [요청 큐잉](https://github.com/TTolsun/libcamera-sdd/blob/279d355ef8f7a4f98bb0a3004c0f788387814506/src/libcamera/camera.cpp#L1330), [중단 처리](https://github.com/TTolsun/libcamera-sdd/blob/279d355ef8f7a4f98bb0a3004c0f788387814506/src/libcamera/camera.cpp#L1445), [Request 재사용](https://github.com/TTolsun/libcamera-sdd/blob/279d355ef8f7a4f98bb0a3004c0f788387814506/src/libcamera/request.cpp#L385), [버퍼 연결](https://github.com/TTolsun/libcamera-sdd/blob/279d355ef8f7a4f98bb0a3004c0f788387814506/src/libcamera/request.cpp#L475)을 검토 시작점으로 삼을 수 있습니다. 위치가 존재한다는 사실만으로 설명이 검증되지는 않습니다.

## 반복 생성 시스템에 반영할 기준

한 번 원고를 고치는 것으로 끝내지 않도록 책임·상태·정상 흐름·오류와 종료·소유권·동시성 질문을 문서 종류별로 정의해야 합니다. 질문별로 사용할 사실과 코드 근거를 공급하고, 답할 수 없는 항목은 별도의 검토 과제로 남겨야 합니다. 클래스 선택 범위 검사는 이 중 일부만 확인합니다.

후속 구현은 근거 수집과 설명 검증을 보강하는 방향이어야 합니다. 근거가 없는 상태도나 호출 순서를 LLM으로 채워 넣거나, 인용 형식만 수정한 뒤 검토 상태를 통과로 바꾸면 안 됩니다. 이번 작업에서는 평가를 기록했으며 공개 원고를 재생성·재배포하지 않았습니다. 사내 HAL에서는 프로젝트 고유의 요청·버퍼·콜백·종료 계약을 다시 검증해야 합니다.
